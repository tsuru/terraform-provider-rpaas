# Plan: Scale Down Behavior no Terraform Provider RPaaS

**Status:** Implemented  
**Branch:** `feat/scale-down-behavior`  
**Upstream PR:** [tsuru/rpaas-operator#192](https://github.com/tsuru/rpaas-operator/pull/192)

---

## Contexto

O rpaas-operator adicionou suporte a configurações de comportamento de scale down para instâncias RPaaS através do PR [#192](https://github.com/tsuru/rpaas-operator/pull/192). Esse suporte foi adicionado tanto ao HPA (HorizontalPodAutoscaler) nativo do Kubernetes quanto ao KEDA (ScaledObject), permitindo controle granular sobre como as réplicas são reduzidas durante períodos de menor carga.

O Terraform Provider RPaaS precisa expor essas configurações para que operadores possam gerenciar o comportamento de scale down via IaC.

---

## Problema

Sem essa feature, usuários do provider não conseguem configurar o comportamento de scale down de suas instâncias RPaaS via Terraform. As opções de scale down ficam fora do controle declarativo, exigindo intervenção manual via CLI ou API direta.

---

## Solução

Estender o recurso `rpaas_autoscale` com um bloco opcional `scale_down` que mapeia os três campos expostos pela API do rpaas-operator:

| Campo Terraform        | Campo API (`ScaleDown`)      | Tipo  | Descrição                                               |
| ---------------------- | ---------------------------- | ----- | ------------------------------------------------------- |
| `units`                | `unitsPolicyValue`           | int32 | Número máximo de pods a remover por período de 60s      |
| `percentage`           | `percentPolicyValue`         | int32 | Percentual máximo de pods a remover por período de 60s  |
| `stabilization_window` | `stabilizationWindowSeconds` | int32 | Janela em segundos para suavizar decisões de scale down |

O bloco `scale_down` é opcional e possui no máximo 1 item (`MaxItems: 1`). Todos os seus campos são opcionais entre si.

---

## Dependências

### rpaas-operator

A versão do `rpaas-operator` utilizada como dependência no `go.mod` deve incluir os modelos `Behavior` e `ScaleDown` no pacote `pkg/rpaas/client/autogenerated`, adicionados no PR #192. Esses modelos são gerados a partir do `openapi.yaml` e expõem:

```
autogenerated.Behavior      -> { ScaleDown *ScaleDown }
autogenerated.ScaleDown     -> { UnitsPolicyValue, PercentPolicyValue, StabilizationWindowSeconds *int32 }
autogenerated.NewScaleDown() -> *ScaleDown
```

A atualização da dependência (`go get github.com/tsuru/rpaas-operator@<versão>`) é um pré-requisito para compilar as mudanças no provider.

## Escopo de Mudanças

### `internal/provider/resource_rpaas_autoscale.go`

1. **Schema** — Adicionar bloco `scale_down` ao `map[string]*schema.Schema` do recurso:
   ```hcl
   scale_down {
     units                = optional int
     percentage           = optional int
     stabilization_window = optional int  # segundos
   }
   ```

2. **`extractAutoscaleFromState`** — Ler o bloco `scale_down` do state e montar o `autogenerated.Behavior{ScaleDown: ...}` para envio à API.

3. **`extractScaleDownFromState`** — Função auxiliar que converte `[]any` do state em `*autogenerated.ScaleDown`, ignorando campos com valor zero.

4. **`resourceRpaasAutoscaleRead`** — Ao ler da API, popular o bloco `scale_down` via `flattenScaleDown` se `autoscale.Behavior.ScaleDown != nil`.

5. **`flattenScaleDown` / `flattenScaleDownNoInput` / `flattenScaleDownWithInput`** — Funções de flatten que respeitam a intenção do usuário: se o usuário não declarou um campo no `.tf`, ele não é importado de volta (evitando diffs espúrios quando a API retorna campos não gerenciados).

- Campo declarado pelo usuário mas não retornado pela API é omitido

## API Mapping (rpaas-operator)

```
PUT /autoscale/{instance}
Body:
{
  "minReplicas": int,
  "maxReplicas": int,
  "behavior": {
    "scaleDown": {
      "unitsPolicyValue":           int,   // optional
      "percentPolicyValue":         int,   // optional
      "stabilizationWindowSeconds": int    // optional
    }
  }
}
```

O rpaas-operator valida que os valores são maiores que zero quando presentes:
- `unitsPolicyValue <= 0` → erro
- `percentPolicyValue <= 0` → erro
- `stabilizationWindowSeconds <= 0` → erro

O provider deve ignorar campos com valor zero ao construir o payload (comportamento implementado em `extractScaleDownFromState`).

---

## Comportamento no Kubernetes

Dependendo de como a instância está configurada, o scale down behavior é propagado para:

- **HPA nativo** (`autoscalingv2.HorizontalPodAutoscaler`):
  ```
  spec.behavior.scaleDown.stabilizationWindowSeconds
  spec.behavior.scaleDown.policies[].type    = Pods | Percent
  spec.behavior.scaleDown.policies[].value   = units | percentage
  spec.behavior.scaleDown.policies[].periodSeconds = 60
  ```

- **KEDA** (`ScaledObject`):
  ```
  spec.advanced.horizontalPodAutoscalerConfig.behavior.scaleDown.*
  ```

## Exemplo de Uso Terraform

```hcl
resource "rpaas_autoscale" "my_instance" {
  service_name = "rpaasv2-be"
  instance     = "my-rpaas"

  min_replicas = 3
  max_replicas = 20

  target_cpu_utilization_percentage = 70

  scale_down {
    # Remove no máximo 2 pods por período de 60s
    units = 2

    # Ou remove no máximo 25% dos pods por período de 60s
    # percentage = 25

    # Aguarda 300s antes de iniciar scale down (default Kubernetes)
    stabilization_window = 300
  }
}
```

## Considerações de State Management

O Terraform faz diff entre o estado declarado no `.tf` e o estado lido da API. O campo `scale_down` tem um desafio específico: a API pode retornar valores de `behavior.scaleDown` que o usuário não declarou (ex: defaults do cluster). Para evitar diffs permanentes:

- A função `flattenScaleDown` usa o estado proposto (`d.GetChange("scale_down")`) para determinar quais campos o usuário gerencia
- Se o usuário não declarou o bloco `scale_down`, nenhum valor é importado de volta
- Se o usuário declarou apenas `units`, somente `units` é sincronizado; `percentage` e `stabilization_window` são ignorados mesmo que a API os retorne

Esse padrão é consistente com o `scheduled_window` do mesmo recurso.
